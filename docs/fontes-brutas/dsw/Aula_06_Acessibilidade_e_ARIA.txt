2. O que é acessibilidade e por que ela importa

Acessibilidade web (a11y) é a prática de construir sites que qualquer pessoa consegue usar — incluindo pessoas com deficiência
visual, auditiva, motora ou cognitiva, que navegam com leitores de tela, apenas teclado, comandos de voz ou outras tecnologias
assistivas.

2.1 Quem se beneficia
   Pessoas com deficiência permanente: cegueira e baixa visão, surdez, limitações motoras, dislexia;
   Limitações temporárias e situacionais: braço engessado, tela sob sol forte, ambiente barulhento, internet lenta;
   Todos os usuários: sites acessíveis são mais rápidos, mais claros e melhor ranqueados (a semântica que ajuda o leitor de tela é a
   mesma que ajuda o Google);
   Você, desenvolvedor: acessibilidade é requisito legal em projetos públicos e diferencial profissional crescente no mercado.

2.2 A exigência legal no Brasil
A Lei Brasileira de Inclusão (Lei nº 13.146/2015), art. 63, determina que é obrigatória a acessibilidade em sites mantidos por
empresas com sede ou representação comercial no país e por órgãos de governo, conforme as melhores práticas e diretrizes
internacionais. Ou seja: para quem vai desenvolver sistemas profissionalmente — o caso de vocês — acessibilidade não é opcional.

2.3 WCAG: as diretrizes internacionais
As WCAG (Web Content Accessibility Guidelines, do W3C) são o padrão de referência mundial, organizadas em 4 princípios — o acrônimo
POUR:

 Princípio                            Pergunta-chave                                Exemplos práticos

 Perceptível                          O usuário consegue perceber o conteúdo?       alt em imagens, contraste suficiente, legendas em vídeo

 Operável                             Consegue operar a interface?                  Tudo funciona por teclado, foco visível, tempo suficiente

 Compreensível (Understandable)       Consegue entender?                            Idioma declarado, rótulos claros, erros explicados

 Robusto                              Funciona com tecnologias assistivas?          HTML válido e semântico, ARIA correto

Níveis de conformidade: A (mínimo), AA (padrão exigido na maioria das leis e contratos — nossa meta) e AAA (máximo).

3.1 Contraste de cores
A WCAG AA exige razão de contraste mínima de 4,5:1 para texto normal e 3:1 para texto grande (≥ 24px ou ≥ 18,5px em negrito). Cinza-
claro sobre branco — tão comum em sites "modernos" — costuma reprovar. Verifique no DevTools (inspecionar a cor do texto mostra a
razão de contraste) ou no WebAIM Contrast Checker (webaim.org/resources/contrastchecker).

3.2 Navegação por teclado e foco visível
Teste fundamental: largue o mouse. Navegue pelo seu site só com Tab (avançar), Shift+Tab (voltar) e Enter (ativar). Três perguntas:
1. Consigo alcançar todos os links, botões e campos?
2. Vejo onde o foco está a cada momento?
3. A ordem do foco segue a ordem visual da página?

  /* Nunca remova o outline sem substituir por algo visível: */
  :focus-visible {
    outline: 3px solid #ffb703;
    outline-offset: 2px;
  }


  CRIME COMUM
   *:focus { outline: none; } sem substituto torna o site inutilizável por teclado. Se encontrar isso em um template ou tutorial,
  corrija.


3.3 Skip link: pulando direto ao conteúdo
Quem navega por teclado precisaria passar por todo o menu em cada página. O skip link resolve — é o primeiro elemento do <body> ,
invisível até receber foco:

  <body>
    <a href="#conteudo" class="skip-link">Pular para o conteúdo</a>
    <header>...</header>
    <main id="conteudo">...</main>

  /* CSS */
  .skip-link {
    position: absolute;
    top: -50px;              /* escondido acima da tela */
    transition: top 0.2s;
  }
  .skip-link:focus { top: 0; } /* aparece ao receber foco via Tab */




4. ARIA: quando o HTML não basta

ARIA (Accessible Rich Internet Applications) é um conjunto de atributos que enriquece o que as tecnologias assistivas "enxergam": papéis
( role ), nomes ( aria-label ) e estados ( aria-expanded ).

  A PRIMEIRA REGRA DO ARIA
  Não use ARIA se um elemento HTML nativo resolve. <button> já é focável, ativável por teclado e anunciado como botão; <div
  role="button"> exige recriar tudo isso na mão — e quase sempre sai errado. ARIA ruim é pior que ARIA nenhum: ele mente para o
  leitor de tela.


4.1 Os atributos que você realmente vai usar

 Atributo                         Função                                                  Exemplo

 aria-label                       Nome acessível para elemento sem texto visível           <button aria-label="Fechar menu">✕</button>

 aria-labelledby                  Nomeia usando o texto de outro elemento                  <section aria-labelledby="titulo-servicos">

 aria-hidden="true"               Esconde do leitor de tela (decorativos)                  <svg aria-hidden="true">...</svg>

 aria-expanded                    Estado aberto/fechado de menus e acordeões               <button aria-expanded="false">Menu</button>

 aria-current="page"              Indica o item de navegação da página atual               <a href="index.html" aria-current="page">

 role="img" + aria-label          SVG informativo (Aula 5)                                 <svg role="img" aria-label="Logo">


4.2 Exemplo integrado: navegação acessível
  <nav aria-label="Navegação principal">
    <button class="menu-toggle" aria-expanded="false" aria-controls="menu">
      <svg aria-hidden="true">...</svg>   <!-- ícone hambúrguer: decorativo -->
      Menu                                 <!-- o texto dá o nome acessível -->
    </button>
    <ul id="menu">
      <li><a href="index.html" aria-current="page">Início</a></li>
      <li><a href="sobre.html">Sobre</a></li>
    </ul>
  </nav>


Observação: alternar aria-expanded entre true / false no clique exige JavaScript — na Unidade 2 fecharemos esse ciclo. Os frameworks
da Aula 4 (Bootstrap/Materialize) já fazem isso em seus componentes — inspecione a navbar no DevTools e observe os atributos mudando.

  VERDADE IMPORTANTE
  Ferramentas automáticas detectam só 30-40% dos problemas de acessibilidade. Nota 100 no Lighthouse não significa site acessível
  — significa que os erros detectáveis por máquina foram resolvidos. O teste de teclado e o leitor de tela são insubstituíveis.



6. Checklist final da Avaliação 1 (entrega até 29/09, 23h59)

1. HTML semântico: landmarks corretos, hierarquia de títulos, um <main> por página;
