2. Middleware: a linha de montagem do Express

No Express, tudo é middleware: funções que recebem (req, res, next) e formam uma corrente. Cada requisição atravessa a corrente
na ordem em que os middlewares foram registrados; cada elo pode examinar/modificar a requisição e decidir: responder (encerra) ou
passar adiante com next() .

 // Middleware de log: roda para TODA requisição
 app.use((req, res, next) => {
   console.log(`${new Date().toISOString()} ${req.method} ${req.url}`);
   next();                              // sem next(), a requisição "trava" aqui
 });

 // Middleware restrito a um prefixo
 app.use("/api", (req, res, next) => {
   res.setHeader("X-API-Versao", "1.0");
   next();
 });


Você já usou dois sem saber: express.static("public") (tenta achar um arquivo; se não acha, chama next() ) e as próprias rotas
(middlewares que só rodam se método + caminho casarem).

2.1 O middleware indispensável: express.json()
Na Aula 10, o front enviou JSON.stringify(dados) no corpo do POST. Para o Express entender esse corpo, é preciso o parser:

 app.use(express.json());     // SEM isso, req.body é undefined — erro clássico nº 1

 app.post("/api/produtos", (req, res) => {
   const { nome, preco } = req.body;                // o objeto enviado pelo fetch

   if (!nome || typeof preco !== "number") {      // validação NO SERVIDOR
     return res.status(400).json({ erro: "nome e preco são obrigatórios" });
   }

   const novo = { id: proximoId++, nome, preco };
   produtos.push(novo);
   res.status(201).json(novo);                    // 201 Created + o recurso criado
 });


  A REGRA DE OURO DA VALIDAÇÃO
  Lembra das camadas (Aula 3)? HTML valida, JS valida — e mesmo assim o servidor valida de novo. Qualquer pessoa pode mandar um
  POST direto para sua API (via curl, Postman ou script), pulando seu front-end inteiro. A única validação confiável é a do servidor.
2.2 Status HTTP que sua API vai usar

 Código                                      Quando devolver

 200 OK                                      Sucesso em consulta/alteração.

 201 Created                                 Recurso criado com sucesso (POST).

 204 No Content                              Sucesso sem corpo (ex.: DELETE).

 400 Bad Request                             Dados inválidos enviados pelo cliente.

 401 / 403                                   Não autenticado / autenticado mas sem permissão (Aula 14).

 404 Not Found                               Recurso ou rota inexistente.

 500 Internal Server Error                   Erro inesperado no servidor.



3. Estruturando o projeto: express.Router

O Router é um "mini-app" que agrupa rotas de um mesmo recurso em arquivo próprio:

 api-projeto/
 ├── public/                  # front-end (Unidades 1-2)
 ├── routes/
 │   └── produtos.js          # todas as rotas de /api/produtos
 ├── data/
 │   └── produtos.js          # os dados (na Aula 15, persistência real)
 ├── server.js                # só configuração e montagem
 └── package.json



 // routes/produtos.js
 const express = require("express");
 const router = express.Router();
 const produtos = require("../data/produtos");

 router.get("/", (req, res) => {          // caminho RELATIVO ao prefixo
   res.json(produtos);
 });

 router.get("/:id", (req, res) => {
   const produto = produtos.find(p => p.id === Number(req.params.id));
   if (!produto) return res.status(404).json({ erro: "Não encontrado" });
   res.json(produto);
 });

 module.exports = router;

 // server.js — enxuto: só monta as peças
 const express = require("express");
 const produtosRouter = require("./routes/produtos");

 const app = express();
 app.use(express.json());
 app.use(express.static("public"));
 app.use("/api/produtos", produtosRouter);   // prefixo + router

 app.listen(3000, () => console.log("http://localhost:3000"));


Novo recurso (ex.: categorias)? Novo arquivo routes/categorias.js + uma linha no server.js . O projeto cresce sem virar espaguete.


4. Tratando o que dá errado

4.1 Rota não encontrada (404 de API)

 // DEPOIS de todas as rotas — só chega aqui quem não casou com nenhuma:
 app.use((req, res) => {
   res.status(404).json({ erro: `Rota ${req.method} ${req.url} não existe` });
 });



4.2 Middleware de erro (4 parâmetros)

 // Assinatura com QUATRO parâmetros = middleware de erro. Vai por último.
 app.use((err, req, res, next) => {
   console.error(err);                          // log completo para o desenvolvedor
   res.status(500).json({ erro: "Erro interno do servidor" }); // resposta genérica p/ o cliente
  });


Qualquer throw em rota síncrona (e, no Express 5, também em rotas async ) cai aqui. Princípio importante: log detalhado no servidor,
mensagem genérica ao cliente — detalhes internos de erro vazados são presente para invasores.
